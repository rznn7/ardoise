# Real-time Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** What other members do shows up on every screen without a tap, through one SSE stream per signed-in user, with exact catch-up after a short drop and a full page reload after a long absence.

**Architecture:** Use cases publish a `GroupChange` through a `REALTIME_PUBLISHER` port after their write commits. A `RealtimeHub` adapter in a new `realtime/` context resolves recipients from membership, numbers events, keeps a replay buffer and serves `GET /events` with Nest `@Sse`. On the frontend one `RealtimeService` owns the `EventSource` and the stores and screens subscribe to its `events`.

**Tech Stack:** NestJS `@Sse` + RxJS, Zod contracts in `@ardoise/shared`, Angular signals, `EventSource`, vitest, testcontainers, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-28-realtime-design.md`

## Global Constraints

- One stream per user: `GET /events`, `text/event-stream`, behind `SessionGuard`.
- Every client message is a JSON `data` line `{ type, ... }`; no SSE `event:` names. Only `ping` has no `id`.
- Event id: `${boot}.${seq}`; `boot` random per process start, `seq` integer from 0. Buffer: last 1000 events. Heartbeat: `{ type: 'ping' }` every 25 000 ms.
- Writes carry `x-op-id` (a `crypto.randomUUID()`); invalid or absent header means no `opId` (`null` on the wire). It is never a 400.
- An event is published only after its transaction commits, and never for a refused write.
- Recipients are read from membership when the event is published, never cached per connection.
- Long absence: `HIDDEN_RELOAD_MS = 5 * 60 * 1000`; `reset` and long absence both call `PAGE_RELOAD`.
- Toast copy: `This payment was deleted`, `This repayment was undone`.
- No comments in code. Commit messages are one line. Run `pnpm typecheck` before calling a task done.

## Review Focus

- A burst: three members add payments within the same second. Each client ends with all three rows once and one balance figure that matches. Pinned in Task 3 (three writes, three events in seq order) and Task 6 (burst → one balance load, three rows).
- My own create: the event arrives before the POST response. Exactly one row throughout. Pinned in Task 6.
- Delete then a late save for the same payment: the row stays gone. Pinned in Task 6.
- Reconnect after a deploy: the server restarted, `Last-Event-ID` is from the old boot. The client gets `reset` and reloads instead of silently missing events. Pinned in Task 2 and Task 5.
- A signed-in user who is not a member opens `/events` while a payment is created in someone else's group. Their stream stays silent. Pinned in Task 3.

  - `replayAfter<T extends { readonly seq: number }>(buffer: readonly T[], current: number, boot: string, lastEventId: string | undefined): readonly T[] | 'reset'`. `buffer` is in ascending `seq`; `current` is the last assigned seq.

### Task 2: The stream: contract, port, hub, `GET /events`

The port lives in `realtime/domain` because the use cases in `payment/`, `settlement/` and the other contexts depend on it. They must see an interface, not a Nest or RxJS class. The hub is infrastructure because it is about delivery (memory, HTTP streaming), not about expenses.

**Interfaces:**
- Shared contract (`realtime.ts`):
  - `OP_ID_HEADER = 'x-op-id'`
  - `realtimeMessageSchema`: a `z.discriminatedUnion('type', …)` over:
    - `payment.saved { groupId, opId: string | null, payment: PaymentResponse }`
    - `payment.deleted { groupId, opId, id }`
    - `settlement.saved { groupId, opId, settlement: SettlementResponse }`
    - `settlement.deleted { groupId, opId, id }`
    - `member.joined { groupId, userId }`
    - `group.created { groupId }`

- `realtime-publisher.ts`:

  - `interface RealtimePublisher { groupChanged(change: GroupChange): Promise<void>; sessionEnded(sessionId: number): void }`. `groupChanged` never rejects: the write is already committed.

  - `auth.controller` `me` returns `.user`.
- `test/helpers/sse.ts`: `openStream(baseUrl: string, cookie: string, lastEventId?: string): Promise<SseClient>`, where `SseClient = { next(timeoutMs?: number): Promise<{ id: string | undefined; data: RealtimeMessage }>; nothing(ms: number): Promise<void>; ended: Promise<void>; close(): void }`.
  - Built on `fetch` with a stream reader.
  - `next` skips `ping`.
  - `nothing` fails if any non-ping message arrives within `ms`.

### Task 6: Stores apply events

The feed store already guards local mutations against racing page loads with `settledMutations`. An incoming event calls the same `markSettled(groupId)`, so a page fetch in flight is discarded and refetched instead of erasing the event.

**Files:**
- Modify: `apps/frontend/src/app/feed/feed-store.ts`, `settlement/done-store.ts`, `balance/balance-store.ts`
- Test: `feed/feed-store.spec.ts`, `balance/balance-store.spec.ts` (existing specs, add cases)

**Interfaces:**
- Consumes: `RealtimeService.events`, `RealtimeService.resynced`.
- `FeedStore`:
  - Generates an opId per `create` / `update` / `remove` / `recordSettlement` / `undoSettlement` and passes it to the api.
  - Keeps `opId → temporaryId` for pending creates and recordings.
  - Keeps tombstones `Set<string>` keyed like `keyOf` (`payment:12`), added on any delete or undo, by event or by own success.
- Event rules, in `FeedStore`'s constructor subscription:
  - `payment.saved` / `settlement.saved`:
    - ignored if tombstoned
    - if `opId` matches a pending create, that temporary row is dropped
    - then `upsert` and `markSettled`
    - `settlement.saved` also calls `done.added`
  - `*.deleted`: tombstone, `patch` out, `done.removed` for repayments, `markSettled`.
  - `resynced`: `loadFirst` for the group whose pages are kept, if any (the same for `DoneStore`).
- `BalanceStore`: events for a group that has a state trigger `load(groupId)`, at most once per `BALANCE_COALESCE_MS = 300` per group. `resynced` reloads every group with a state.

  - a second `payment.saved` with the same id replaces it
  - a `payment.saved` older than the boundary is not shown
  - an edit moving the date past the boundary hides it
  - `payment.deleted` removes it
  - a `payment.saved` after `payment.deleted` for the same id stays removed
  - own create:
    - event with matching opId before the POST resolves → one row, not pending
    - then POST resolves → still one row
  - an event during an in-flight first-page fetch survives the response
  - `settlement.saved` reaches Done; `settlement.deleted` leaves Done
  - a pending local update overlay survives a `payment.saved` for that row
