# Balances Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show my balance on every group row and in the group hero, and a Balances tab with every member's balance and the simplified repayments.

**Architecture:** A new backend bounded context `balance/` computes net balances and greedy debt simplification as pure domain functions over per-member totals that a Drizzle adapter aggregates in SQL. Two read-only endpoints serve them. The frontend adds a `src/app/balance/` feature (API service, store, rows, tab component), a `balance-bar` building block, and wires the group page (hero balance, Payments / Balances tabs) and the home rows.

**Tech Stack:** NestJS 12, Drizzle, PostgreSQL, Zod (`@ardoise/shared`), Angular 22 signals, spartan helm, Tailwind 4, vitest, testcontainers + supertest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-26-balances-design.md`

## Global Constraints

- Money is integer cents everywhere. No floats, including in bar ratios sent over the wire (ratios are computed client-side only).
- Balances of a group sum to 0; `netBalances` throws `UnbalancedLedger` otherwise.
- Greedy simplification: largest debtor pays largest creditor `min(|debt|, credit)`; ties broken by lowest `memberId`.
- Group balances route: `GET /expense-groups/:groupId/balances` (the spec wrote `/groups/...`; the existing convention is `/expense-groups/:groupId/payments`, so we follow it). Mine: `GET /balances/mine`.
- Non-member → 403 `{ error: 'NOT_A_MEMBER' }` (existing `NotAMember` + `MemberExceptionFilter`).
- Copy, exact: hero "You owe" / "Owed to you" / "Settled up"; tabs "Payments" / "Balances"; sections "Balances" / "Repayments"; rows "You pay Léa", "Tom pays you", "Tom pays Léa"; "All settled"; empty state "Nothing to settle yet" with description "Add a payment with + to see who owes whom."
- Feature templates: Tailwind layout/spacing and theme colours only, text directives for type, no arbitrary values, no inline styles, no component `.css`. Inline `[style.width.%]` is allowed only inside `shared/ui`.
- Near-zero comments. Commit messages are a single line.
- `pnpm typecheck` before calling any task done (vitest and eslint don't typecheck).

## Review Focus

1. A member who joined but never paid nor was included in a split: appears with 0, never missing from the list (SQL left join). Test in Task 2.
2. A payer excluded from their own split: credited the full amount, owes nothing for it. Test in Task 2.
3. A payment added, edited or deleted while the group page is open: hero and tab refresh once the server confirms, not before. Test in Task 5.
4. A group where every balance is 0 but payments exist vs. a group with no payments: "All settled" vs. "Nothing to settle yet", and the hero shows "Settled up" vs. nothing. Tests in Tasks 7 and 8.
5. Reloading on `?tab=balances` keeps the tab, and back from it goes home, not to the Payments tab. Test in Task 8 and Playwright in Task 10.

### Task 1: Net balance and debt simplification (pure domain)

**Files:**
- Create: `apps/backend/src/balance/domain/balance.ts`
- Create: `apps/backend/src/balance/domain/net-balances.ts`
- Create: `apps/backend/src/balance/domain/simplify-debts.ts`
- Test: `apps/backend/src/balance/domain/net-balances.spec.ts`, `apps/backend/src/balance/domain/simplify-debts.spec.ts`

Why here: these are the business rules of what a balance is and how a group settles. No Nest, no Drizzle, so they belong in `domain/` and are unit-tested in isolation (the one case where the project writes unit specs).

**Interfaces:**
- Produces (`balance.ts`):
  - `type MemberTotals = { readonly memberId: number; readonly paid: number; readonly owed: number }`
  - `type MemberBalance = { readonly memberId: number; readonly amount: number }`
  - `type Transfer = { readonly fromMemberId: number; readonly toMemberId: number; readonly amount: number }`
  - `class UnbalancedLedger extends Error {}`
- Produces: `netOf(totals: MemberTotals): number` (paid − owed) and `netBalances(totals: readonly MemberTotals[]): MemberBalance[]` in `net-balances.ts`; same order as input; throws `UnbalancedLedger` when the sum ≠ 0.
- Produces: `simplifyDebts(balances: readonly MemberBalance[]): Transfer[]` in `simplify-debts.ts`.

- [ ] **Step 1: Write the failing specs**

`net-balances.spec.ts`:
- `netBalances([{memberId:1,paid:3000,owed:1000},{memberId:2,paid:0,owed:2000}])` → `[{memberId:1,amount:2000},{memberId:2,amount:-2000}]`
- a member with `paid:0, owed:0` → `amount: 0` and is kept
- `netBalances([{memberId:1,paid:100,owed:0}])` throws `UnbalancedLedger`
- `netBalances([])` → `[]`

`simplify-debts.spec.ts` (helper `settles(balances, transfers)` that applies every transfer and expects all amounts to reach 0):
- one debtor, two creditors: `[{1:+3000},{2:+1500},{3:-4500}]` → `[{from:3,to:1,amount:3000},{from:3,to:2,amount:1500}]`
- many to many: `[{1:+8820},{2:+3360},{3:-2110},{4:-4250},{5:-5820}]` → settles, and `transfers.length <= 4`
- already settled `[{1:0},{2:0}]` → `[]`
- ties: `[{1:+1000},{2:+1000},{3:-1000},{4:-1000}]` → `[{from:3,to:1,amount:1000},{from:4,to:2,amount:1000}]`
- every transfer amount is a positive integer

- [ ] **Step 2: Run them, expect FAIL**

Run: `pnpm --filter @ardoise/backend test -- src/balance`
Expected: FAIL, modules not found.

- [ ] **Step 3: Implement `balance.ts`, `net-balances.ts`, `simplify-debts.ts`**

`simplifyDebts`: copy the non-zero balances into mutable debtors (amount < 0) and creditors (amount > 0); loop while both are non-empty: pick the debtor with the largest `|amount|` (tie: lowest `memberId`) and the creditor with the largest amount (tie: lowest `memberId`), push `min(|debt|, credit)`, subtract from both, drop whoever reaches 0.

Why a store: the group page and the Balances tab read the same data, and it must refetch when a payment mutation settles. The trigger comes from `PaymentStore`, which already counts settled mutations per group.

**Interfaces:**

A reload keeps showing the last loaded value (no flash back to loading), and a failed reload after a success keeps the old value; only a first-load failure yields `error`. Ignore responses of superseded loads.
